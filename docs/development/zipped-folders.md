# Zipped folders

A zipped folder keeps its contents in an archive and is unzipped while it is used. This page is about how that works on disk and why it never loses anything, and lists the edge cases. What admins set and users see is in [Archived directories](../administration/archived-directories.md). Built so far (`Features/ZippedFolders`): the core (zipping, unzipping, checking and recovering a folder's archive), `archive` in `.config.json`, turning it on and off, a new `filetype`, `onLowestLevel`, encryption, unzipping on demand, zipping when idle, and recovering at startup. Copying, moving, renaming and deleting them (see below), the archive button, and downloading one as it is (admins). Uploading archives comes next.

## In the app (`ArchivedFolders`, `ArchiveGate`)

- **Mounted like a bridge.** An unzipped copy is a location of its own while it is unzipped (`EntryLocations.MountArchive`, with `IsArchive`), mounted where the folder is, with its own history (`HistoryService.ArchiveUnzipped`, `ArchiveZipping`). Its history is opened, and what is pending committed, in the background: the first commit of a folder just made an archived one holds everything in it, and would keep the save of its configuration waiting (also for the history's lock, while a commit of the others runs). What changes in it before that goes into that commit, without its author. Zipping it waits for that first. Everything that goes through the locations (paths, listings, permissions, passwords, the history) sees it as the folder. The locations are replaced as a whole when one comes or goes, so a reader always sees one state.
- **Its configuration stays outside** (`EntryLocations.ConfigDirectoryOf`): the folder's own `.config.json` is next to the archive, and is the configuration of the copy's root too. A password of the folder is the same protection zipped and unzipped (`PasswordLocks` keys it by the folder).
- **The gate** (`ArchiveGate`, in front of every request of an entry): holds a use of every unzipped folder along the path until the answer is sent, and unzips the outermost zipped one first (for who may open it). It waits `Archives:WaitSeconds`; after that, a page shows `_Unzipping` (which asks `?unzip` of the folder), and a script's request gets 503 with `X-Notes-Unzipping`, which `_Unzipping.ts` waits for and sends again. What works on the folder as a whole (`?config`, `?selection`, `?unlock`, `?lock`, a DELETE) doesn't unzip it. A rename does, so that what is in it is checked as for any directory, but holds no use of it: `RenameHandler` zips it after the checks and renames the folder next to its archive.
- **Copy, move, delete, rename** (`TransferService`, `RenameHandler`): every archived folder at or in what they take is unzipped first (`UnzipAllAtOrBelowAsync`, for who may open it) and held in use while the planner checks it, so what is in it is checked as for any directory. A copy copies that (a normal directory). A move, delete or rename then zips them, holds their gates so none is unzipped meanwhile (`WhileZippedAsync`), and takes each as its configuration and archive (`TransferService.AsZipped`), also for those who don't manage configurations.
- **The archive button** (`ZipHandler`, `POST ?zip`): zips every unzipped folder the user may open (`ZippableFor`, asked of the copies), in the background, as zipping a big one takes long; the answer only says where the page goes. The gate lets it through without holding or unzipping anything, which would keep the folder it is asked from from being zipped.
- **Downloading it as it is** (`ArchiveHandler`, `POST ?archive=as-is`, admins): a job like the other downloads, which zips the folder (if it is unzipped) and copies its archive to the prepared downloads. Copied rather than handed out from where it is, so zipping it again later (a rename over it) never meets an archive that is being downloaded. `?archive` other than `=directory` and `=selection` (asking how far it got, downloading what was made, as-is) works on the folder as a whole in the gate, so the page's polling never unzips it again.
- **While it is zipped** (`ZipJob` of the folder, from when zipping takes its gate until it ends): it is `ArchiveState.Zipping`, with how far it got (writing the archive is 0–70 %, reading it back the rest). The listing shows a bar after its name, which `_Unzipping.ts` keeps up to date with `GET <folder>?zipping` (`ZippingHandler`; the gate lets it through without holding or unzipping anything) and turns into the mark it ends as. The as-is download shows it as the first 80 % of its bar.
- **Opening it stops the zipping** (`ZipJob.StopBecauseOpened`, from `UseAsync` and `Unzip`): a zipping that only saves space (the idle job, the archive button, the as-is download) is cancelled, the `.new` archive deleted and the copy, untouched, mounted again, so there is nothing to unzip. Up to the rename over the old archive; after it, it finishes and the folder is unzipped again. Stopping the zipping of a folder also stops that of the folders inside it it was zipping first. A zipping that a move, delete, rename or conversion waits for is never stopped: opening waits for it.
- **A folder being written counts as zipped** (`IsZipped`): it isn't mounted then and, the first time, has no archive yet, so a request that came in would otherwise see the folder empty. It unzips it instead, which stops the zipping or waits for it.
- **Waiting for uses has a limit** (30 s): a delete asked for from a page inside the folder holds a use of it itself. It fails then (409), and nothing changes.
- **Its archive is no entry** (`EntryAccess`): nobody, admins neither, may read `_.7z` of an archived folder, so whatever walks a directory (downloads, selections, transfers) leaves it out rather than hand out what is in it whole.
- **The lock of each folder:** a gate (`SemaphoreSlim`) held while it is zipped or unzipped, and a count of uses. Zipping holds the gate (nothing new starts to use it) and waits until no use is left; the job that zips idle folders only takes those that aren't used at all. Folders unzipped inside one are zipped before it.
- **Whether a folder is archived** (`ArchiveSettingsResolver`): its own `archive` (enabled, not `onLowestLevel`), or, if it sets none (or `null`), the nearest folder above that sets one, if that one is `onLowestLevel`: then it is archived with those settings if it holds files and no folder between does, or if it is archived on disk already (a copy mounted or in `_/temp/unzipped`, or an archive: once archived it stays so). The search stops at a bridge. An invalid configuration on the way makes it uncertain (`ResolvedArchive.IsCertain`), and nothing is turned on or off then.
- **The code:** `ArchivedFolders.cs` (what a folder is, using, unzipping, zipping), `ArchivedFolders.TurningOnAndOff.cs` (turning on and off, reconciling, `onLowestLevel`), `ArchivedFolders.Recovery.cs` (the start), `ArchivedFolders.Encryption.cs` (unzipping and zipping for encryption changes), one class in four files as they share the folders' gates and what is mounted; `ZipJob`, `UnzipJob`, `ArchiveSettingsResolver`.
- **Paths found before the lock** (`WhereItIsNow`): a create, an upload, a copy or a move works out its directory before it waits for the `StructureLock`; if the folder was made an archived one meanwhile, the path is mapped into its copy under the lock. Otherwise what it writes would land next to the archive, hidden by the copy.
- **Right after a change** (`ArchiveLowestLevelAfterChangeAsync`, from creating a file, uploading, copying and moving): below an `onLowestLevel` folder, the directory that got something is reconciled at once, so a folder that holds files now is archived (and mounted) before the answer is sent.
- **Bringing the disk in line** (`ReconcileAsync`, after a configuration's `archive` changed, after a move, at the start, by the soft restart (`ReconcileEverywhereAsync`, `SoftRestartJob`), and for `onLowestLevel` folders and unzipped folders whose turning off failed by the job): finds below a folder what is archived on disk but certainly not by the configurations (turned off), and what is archived by them but not on disk (turned on), the outermost first, and looks again after each turning off (what was in its archive comes to light). A failure of the folder itself whose configuration was saved puts its configuration back (409); others are logged and tried again later.
- **Turning it on** (`ConvertAsync`): the folder is renamed into its copy (one step), made again, and its configuration moved back next to where the archive will be.
- **Turning it off** (`TurnOffAsync`): folders unzipped inside it are zipped first (their copies are in its copy's `_/temp`), what uses it is waited for (30 s), then a marker naming the folder is written into `_/temp/zipping/turning-off/<id>.target`, and the copy is renamed to `<id>` next to it (or the archive unzipped there). From then on that copy counts: the archive is deleted, its `_/history` moved to `_/archived-history/<path>/<time>` of the location (a repository inside another's work tree would be tracked by it), the rest of its `_` deleted (work of zipping inside it), and its entries moved into the folder one by one. At the start, each marker with its directory is finished (`RecoverTurningOff`); one without is deleted (nothing had moved).
- **How far it got** (`Helpers.WorkStatus`, `WorkPhases`): besides the fraction for the bar (`IProgress<double>`), zipping and unzipping tell what they are doing (`Action<WorkStatus>` of `FolderArchiver.ZipAsync`/`UnzipAsync`, kept by `ZipJob.Status` and `UnzipJob.Status`), and so do the archives made to be downloaded (`ArchiveJob.Status`, counted by `ArchiveProgress`) and the unzipping of uploads. Every answer about how far something got (`?unzip`, `?zipping`, `?archive=<id>&progress`, `?unzipping`) has it as `status`; `describeProgress` in site.ts says it in words (`ProgressTexts`). A status of `waiting` is drawn as an hourglass in place of the bar (`showPending`), with what it waits for (`WorkStatus.WaitingFor`, the title of that operation) where it is known. Every such piece of work is in the list of running operations while it runs (`Operations.StorageOperations.Begin`, with how to cancel it), which the toolbar's hard drive button shows (`OperationsHandler`, `_Operations.ts`).
- **Encryption** (`ArchivePasswords`, `ArchivedFolders.Encryption.cs`, `ArchiveEncryptionChanges`, `ArchivePasswordPrompt` for what has to zip it without the password known): the password of the folder that sets the archive up (`ResolvedArchive.SettingsFolder`) is kept in memory from a right password (dialog or header, `IPasswordWitness`) until no unzipped folder needs it (`ForgetPasswordIfUnneeded`), and only used while the configuration has the hash it was found right for. Whether an archive is encrypted is read from the archive (`ArchiveReading.IsEncrypted`), not from the settings, which may have just changed. Unzipping one without the password ends with `UnzipJob.NeedsPasswordOf`; the gate then drops the browser's unlock (`PasswordUnlocks.Lock`), so the password prompt asks for it. Zipping one without it doesn't start (it stays unzipped, logged). The copy of an encrypted folder (the trash of zipping, a failed unzipping's staging) and every leftover in the work directories at the start are overwritten (`Shredding`, `Archives:OverwritePasses`) before they are deleted; an unencrypted archive that an encrypted one replaces too (`ArchivedFolder.ShredsReplacedArchives`), while the copy still counts. Turning encryption off or changing the password unzips the encrypted archives (at and below the folder) with the known password before the configuration is saved; turning it on unzips and zips the zipped ones in the background (`ReencryptInBackground`). The lock button zips those behind what it locks (`ZipEncryptedInBackground`).
- **A new `filetype`** is written at the next zipping: `_.zip.new` takes the place of `_.zip` as usual, then the old `_.7z` is deleted (`ArchivedFolder.FormerArchivePath`), before the copy is taken away, so two archives are only there while the copy counts. If the app stopped in between, the older one is deleted at the start.
- **`onLowestLevel`** (`ConfigHandler`): turning it on is refused over entries with a password or folders archived with settings of their own below (`DirectoriesBelow`), and sets `"archive": null` in the configurations below (`ConfigText.SetArchiveToInherit`). The job remembers the `onLowestLevel` folders found and reconciles them every run, so folders that come to hold files are archived.
- **At startup** (`RecoverAsync`, before the first request): the work directories are emptied, a copy whose folder is gone (a conversion that stopped half way) gets its folder and configuration back, copies that are there are mounted, and folders that are turned on but not converted are converted.

## On disk

For a zipped folder `parent/foo` in a location (the root or a [bridge](../administration/bridges.md)):

| Path | What it is |
|---|---|
| `parent/foo/.config.json` | The folder's own settings, readable without unzipping (permissions, `zip`, `passwordHash`). |
| `parent/foo/_.7z` or `_.zip` | The archive: everything in the folder, with its own `.config.json` files and its history (`_/history`). |
| `parent/foo/_.7z.new` | Only while it is zipped again: the new archive, before it replaces the old one. |
| `parent/foo/_.7z` and `_.zip` | Only while the `filetype` is changed: between the new one taking its place and the old one being deleted (the copy counts). |
| `_/temp/zipping/turning-off/<id>` and `<id>.target` | Only while archiving is turned off: the copy, which counts, and the marker naming the folder (relative to its location). |
| `_/archived-history/parent/foo/<time>` | The folder's own history from while it was archived, set aside when it was turned off. |
| `_/temp/unzipped/parent/foo` | Only while it is unzipped: its contents, which are what counts then. |
| `_/temp/zipping/unzipping/<id>` | Only while it is unzipped: the archive being unzipped. |
| `_/temp/zipping/deleting/<id>` | Only while the unzipped copy is deleted, once it is zipped. |

The `_/temp` folders are those of the folder's location, so on the same volume as the folder: everything below moves things with renames, which only work within a volume and either happen or don't.

## Zipping and unzipping (`FolderArchiver`)

Zipping, from the unzipped copy:

1. The new archive is written to `_.7z.new`, next to the old one. The SHA-256 of each file is worked out while the writer reads it.
2. It is flushed to the disk, then read back from the disk: it must hold exactly those files with those hashes, and the same directories (also the empty ones). Otherwise it is deleted, and the zipping fails with nothing else changed.
3. It is renamed over the old archive, and its directory flushed.
4. Only then is the unzipped copy renamed into `_/temp/zipping/deleting` (so it is gone at once, never half there) and deleted there.

Unzipping is the other way round: into `_/temp/zipping/unzipping/<id>`, every file and directory flushed to the disk, then renamed into `_/temp/unzipped/…`. Until that rename, the archive is what counts.

**The rule recovery relies on:** if the unzipped copy is there (in `_/temp/unzipped`), it holds everything, and the archive may be older. If it isn't, the archive holds everything. A `.new` archive and anything in `_/temp/zipping` are only ever half done, and are deleted (`Recover`, `RecoverWorkDirectory`). The tests stop at every step (`ArchiveStep`): they copy what is on disk at that moment, recover the copy, and check that it still holds everything (`FolderArchiverTests`).

Neither may run twice at once for the same folder, nor while its unzipped copy is being changed: that is up to the caller (a lock for each folder, with the next step).

### Flushing to the disk

A power cut loses what the system had not written to the disk yet, and not necessarily in the order it was written. So each step flushes what the next relies on (`DurableFiles`): the new archive before it is checked, the directory of the archive after the rename (before the copy is deleted), and each unzipped file and directory before the copy is renamed into place. Otherwise a power cut right after unzipping could leave files that are empty, which would then count as the folder's contents and be zipped as they are.

On Linux a directory is flushed with `fsync` of the C library, which .NET has no call for. Windows has no such step: NTFS keeps changes to directories in its journal. A rename on Windows (`File.Move`) is not written through to the disk at once; if a power cut loses it, the old archive and the unzipped copy are still there, and the copy counts.

## Edge cases

| Case | What happens |
|---|---|
| The app stops while the new archive is written, checked, or before it replaces the old one | The old archive and the unzipped copy are untouched; the `.new` is deleted at the next start, and the copy still counts. |
| The app stops after the new archive replaced the old one, before the copy is gone | The copy and the archive hold the same; the copy counts, and zipping it again changes nothing. |
| The app stops while the copy is deleted | It was renamed into `_/temp/zipping/deleting` first, so it is no copy any more; the rest of it is deleted at the next start. |
| The app stops while unzipping | What was unzipped is in `_/temp/zipping/unzipping` and is deleted at the next start; the archive counts. |
| The new archive doesn't hold what was zipped (a disk or library fault) | It is deleted, the zipping fails, and the old archive and the copy stay. |
| Taking the copy away fails, after the archive was replaced (a file of it is open, on Windows) | The zipping fails; the copy is still there and counts, and the archive holds the same. |
| Deleting what was taken away fails | Logged as a warning, and tried again at the next start. Zipping itself worked. |
| A wrong password, or a damaged archive | `ArchiveUnreadableException`; nothing is unzipped. |
| An entry of the archive whose path leads out of the folder (`..`), or that no file can be named on this system | The archive can't be unzipped (`ArchiveUnreadableException`). A leading `/` is taken off. |
| An entry that is there twice, or twice but for case on a file system that doesn't tell them apart | The archive can't be unzipped; neither replaces the other. |
| `\` and `:` in names | Fine on Linux, where they can be in a name; on Windows `\` in an archive counts as a `/`. |
| A link (symbolic link, junction) in the unzipped copy | Left out of the archive, with a warning in the log: it could point anywhere. The app itself never makes links. |
| Hidden and system files, and the folder's `_` (its history) | Go into the archive like anything else. |
| Read-only files (git writes its objects that way) | Zipped like the others; unzipped as normal files. |
| Times of the files | Kept (a 7z keeps them as UTC, a zip as local time, to two seconds). Times of directories are not kept. |
| An empty folder | Zips to an archive with nothing in it, which unzips to an empty folder. |
| The app stops while a folder is turned into an archived one | Before the rename, nothing changed (the configuration says it is on, and it is converted at the next start). After it, the copy holds everything; the next start makes the folder again and puts its configuration back. |
| A request uses the copy while it would be zipped | Zipping waits until it is answered. A page's request that comes after (an edit saved later) finds it zipped, gets 503, and the page unzips it and sends it again. |
| Zipping fails while the app runs | The copy stays mounted and counts, as before; the next idle run tries again. |
| An archived folder inside another one | Unzipped into the copy of that one (its `_/temp/unzipped`), once that one is; zipped before it. The `_/temp` of a copy is never put into its archive. |
| A rename of the folder, or of one above it, while it is unzipped | It is zipped first, so that its archive moves with the folder; it is unzipped again where it is then. |
| Unzipping fails (a damaged archive) | The request answers 500 and says so; the archive is as it was, and the next request tries again. |
| The archive button while someone works in a folder | That folder is zipped once their request is answered (30 s at most, then it stays unzipped until the idle job gets to it). A page of theirs that sends something later unzips it again. |
| An as-is download while the folder is unzipped and in use | It waits like any zipping (30 s at most), then says the folder is in use; nothing changes. |
| The folder is opened while it is zipped | The zipping stops (where it may, see above) and the copy is used as before; the same if it is opened while zipping waits for its uses. An as-is download that was zipping it says the folder is in use. |
| The folder is opened just after the new archive replaced the old one | Too late to stop: it is zipped, then unzipped again for whoever opened it. Wasted work, nothing lost. |
| A request while the folder is zipped for the first time | It waits for the folder (or stops the zipping) instead of finding it empty: the folder counts as zipped while it is written. |
| Zipping a folder with archived folders unzipped inside it, stopped | Those it already zipped stay zipped until they are opened. |
| The app stops while archiving is turned off | Before the copy is moved next to the marker: nothing changed, the marker is deleted, and turning it off is done again (the configuration says so). After: the copy counts, and what is left (deleting the archive, setting the history aside, moving the entries) is finished at the start. |
| An entry of the copy whose name is in the folder already, when it is turned off | Can't be (the folder holds only its configuration then); if it is, it stops with an error, and what is left stays in the work directory, which counts. |
| An invalid configuration of an archived folder (or of one above that decides it) | Never counts as turned off: nothing is changed until it is fixed. |
| Archiving turned off in the file while the app didn't run | Done at the start (reconciled), unzipping the archive into place if it is zipped. |
| A user's file named `_.7z` or `_.zip` | Can't be made in the app (reserved names). One put there from outside is no entry, and makes the folder count as archived on disk: don't. |
| Below an `onLowestLevel` folder, a folder that held only folders gains a file | It is archived too (by the job), with the archived folders below it inside (nested archives); those stay archived. |
| An archived folder below an `onLowestLevel` one is moved out from under it | It is turned off where it is then (reconciled after the move). |
| An `onLowestLevel` folder inside an archived folder | Saved with a warning (nested archives only make sense with encryption). Its folders are archived when it is saved, and when they come to hold files in the app. Ones that come to hold files on the server: by the job while it knows of it (it forgets it when the outer one is zipped), otherwise at the next start or soft restart. |
| Something is created in a folder while it is made an archived one | The create (upload, copy, move) waits for the structure lock, then finds the folder in its copy (`WhereItIsNow`), not next to the archive. |
| The app stops while an encrypted folder is unzipped | Its copy counts and is mounted at the start, as always, but isn't zipped (the password is gone with the memory) until someone unlocks it; logged. Plaintext on disk until then. |
| The app stops while an encrypted folder's copy is overwritten (after zipping) | It was renamed into the work directory first; the start overwrites and deletes what is left. The archive counts. |
| The password changes while an encrypted folder is unzipped | The new one is kept (it was typed), the old archive was unzipped first: it is zipped with the new one. A password in memory whose hash isn't the configuration's any more is never used. |
| Someone has it unlocked, but the app forgot the password (it was zipped meanwhile, or the app restarted) | Opening it asks for the password again; the unlock is dropped. |
| An unzipped encrypted folder is moved, renamed, deleted or downloaded as it is without its password known | It can't be zipped for it: before anything is done, `ArchivedFolders.UnknownPasswordToZipAtOrBelow` finds that, and `ArchivePasswordPrompt` answers with the password prompt (403, `X-Notes-Password-Required`), dropping the browser's unlock first (unlocking what is unlocked checks nothing, so the app wouldn't learn the password). The page's scripts ask and send the request again. Nothing changes until then. |
| A 7z encrypted archive is slow to open | 7-Zip's key derivation runs each time it is opened (checking, counting, unzipping): a second or so more per unzipping and zipping. |
| Large folders | Unzipping and zipping report how far they got; zipping and unzipping take time and processor, which is why they run outside the app's global lock (next step). Each unzipped file is flushed to the disk, which makes unzipping many small files slower. |
